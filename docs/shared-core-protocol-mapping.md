# Shared-core Interface coverage: A2UI over A2A and A2UI over AG-UI

Working architecture check, September 13, 2026. This maps the [25 existing requirements](a2a-vs-ag-ui-requirements.md) through the proposed Exo core (kept private) and each independent protocol Adapter. It records source inspection, possible mappings and missing contracts. It is not an implemented Interface, an accepted specification, a new runtime test result or a protocol selection.

**Finding:** The proposed Modules provide plausible homes for the required behavior, but the public Interface is not yet demonstrably complete. The main gaps are original contribution preservation, progressive output, targeted input/continuation, truthful cancellation, typed failure outcomes and capability/query contracts. A small Interface can express these; four method names alone do not establish them.

**Revision follow-up:** This table records the audit of the initial sketch. The [revised Interface proposal](shared-core-interface.md) now supplies record families, operation semantics, ordering/failure rules and provisional policies for the gaps below. Its [coverage crosswalk](shared-core-interface.md#revision-coverage-and-remaining-decisions) distinguishes proposed coverage from outstanding implementation/proof. The original Core gap labels remain audit findings; they do not mean the revision omitted those contracts. Actual spike losses, native mapping costs and scores remain unchanged.

**September 14 runtime follow-up:** Interface revision 2 additionally represents host-only trigger causes, effective execution profiles/exact invocation authority, derived-context lineage, optional executable checkpoints, work-wide budgets and host supervision, informed by the cross-runtime audit (kept private). These refine shared responsibilities behind R04/R07–R09/R15–R20 and C02–C04; they do not add protocol-native guarantees or change this historical matrix's tested evidence. Its [updated projection obligations](shared-core-interface.md#protocol-projection-obligations) explain how either Adapter preserves these facts. A private trigger admission is not a fifth browser operation, and an observer checkpoint cannot become executable state.

Both columns retain A2UI, Lit and a Pi-based Exo host. The intended shared-core topology has sibling Adapters: neither calls through the other. Each enabled Adapter must preserve the behavior it exposes. A feature available only through an Exo convention still has integration cost; a native feature that the core cannot supply must not be advertised as supported.

## How to read this check

R01–R25 correspond, in order, to the existing requirement table. C01–C04 unpack cross-cutting contract questions; they do not add four accepted product requirements. The core representations below are illustrative types and behavior, not selected TypeScript declarations or new public endpoints.

- **Actual loss:** source inspection identifies information discarded or required behavior excluded by a delivered spike.
- **Core gap:** the proposal has an owner or operation name, but the relevant type, ordering, lifecycle or failure contract is missing or ambiguous.
- **Mapping cost:** behavior can be represented, with additional owned translation or a documented restriction.
- **Unproved:** the intended behavior has not been demonstrated at the necessary scope. This is different from a proven loss or a protocol limitation.
- **No inherent loss identified:** the mapping has no identified semantic obstacle; the Implementation and its proof may still be incomplete.

“Observed” in the tables means inspected source or previously recorded execution, explicitly distinguished. “Available” means a protocol/SDK capability. “Proposed” means our intended mapping. None of these labels upgrades a source inspection to a passing reliability test. Evidence references are collected under [Evidence and inspection scope](#evidence-and-inspection-scope).

## Focused contract gaps

These rows sharpen existing requirements, rather than selecting every available native feature for v1.

| Required behavior | Core representation and owner | A2UI over A2A mapping | A2UI over AG-UI mapping | Information/capability lost, or work still required |
| --- | --- | --- | --- | --- |
| **C01 — Preserve useful incremental output, if exposed** | Runtime emits typed output/tool updates with output/tool identity, work/turn association, append/replace meaning, order and provisional/final/failed status. Conversation retains meaningful completed output; Observation defines live delivery and reconstruction. | Proposed: task status messages and Artifact updates with explicit Exo output/tool correlation. Pinned resubscribe ignores standalone executor Message events; do not place observer progress there and assume delivery. | Proposed: map real in-progress output to text/tool/activity events, retaining stock processing where the client uses it. Tool argument completion, execution result and run completion must remain distinct. | **Core gap.** A final snapshot cannot recover tool IDs, original progression or causal detail never recorded by Runtime. Durable retention of every token is not required: specify which output is transient, how current output is reconstructed, and which meaning is archived. |
| **C02 — Ask for input that blocks specific execution** | Runtime owns InputRequest identity, target work/tool, blocking scope, expected response, expiry/resolution and continuation policy. Conversation records question/answer; Workspace owns any proposal/effect. Authorization-needed is distinct from generic failure. | Available: INPUT_REQUIRED or AUTH_REQUIRED on tracked work, then task-targeted continuation. Proposed: explicit Exo question/answer association; terminal work requires a new execution association rather than reopening a terminal Task. | Available but unintegrated: interrupt outcome plus linked resume responses. The native rules require addressing all open interrupts and block new input on that thread. Pinned client initialization also checks pending interrupts before connect. | **Semantic mismatch requiring a decision.** Job-scoped questions and independently usable thread observation do not automatically fit native AG-UI thread suspension. No silent bypass or new-client reset constitutes cross-client enforcement. |
| **C03 — Retry, continue and stop without confusing outcomes** | Host: immutable AdmissionReceipt with normalized request identity; Runtime: targeted follow-up/steer/answer/cancel outcome and current work truth; Workspace: separate EffectOutcome. Define duplicate versus conflicting reuse, permissions, deadlines and status lookup. | Message IDs can carry correlation but do not supply our all-command replay contract. CancelTask completion/terminal errors need deliberate projection; native streaming submission is not covered by the spike's non-streaming admission path. | Exo request/result convention carries receipts. | **C04 — Expose honest capabilities, queries and failures** | Host provides only implemented capability facts, typed absence/refusal/failure and caller-required scoped queries. Native work results, client-provided tools, attachments or richer media need an actual product use case and mapping before support is promised. A checkpoint Artifact is not automatically each work Task's result. |

## Proposed Interface amendments

These are architecture proposals exposed by the check. They preserve the five existing Module owners and require no protocol-specific domain subsystem. Operation names and packaging remain open.

| Interface area | Proposed explicit contract | Owner | Coverage | Decision or proof still needed |
| --- | --- | --- | --- | --- |
| Contribution and exact reference | Original action plus normalized intent; optional utterance/data model; authored identity, historical surface/source reference and causal target. Define when drafts become contributions. | Conversation; Host admission | R02–R05, R10, R20 | Same event through each Adapter must retain the same original provenance and produce equivalent context, including resolved form values. |
| Admission and control results | Stable logical request/fingerprint; original receipt; typed conflict/refusal/absence; associated turn/work/effect IDs; current truth fetched separately. Target new work, follow-up, steering, answer and stop explicitly. | Host; Work Runtime; Workspace for effects | R08, R11, R15–R17, C03 | At least two concurrent callers, same/different request IDs, lost responses, late stop, restart and saturated admission. A2A completion and AG-UI acknowledgement mappings must remain truthful. |
| In-progress output and reconstruction | Typed output lifecycle, identity/order, append/replace and final/error association. Define transient delivery relative to committed revisions; preserve meaningful completed output and reconstructible current state. | Work Runtime produces; Conversation retains meaning; Observation delivers | R02, R12–R13, R19, C01 | Decide which live detail the product actually needs. Test real incremental Pi output and mid-output reconnect; do not synthesize a purported original stream from a final snapshot. |
| Blocking input and continuation | InputRequest separated from Proposal; work/tool target, suspension scope, expected answer, expiry, resolution, authorization-needed and resume policy. | Work Runtime; Conversation; Workspace for domain decisions | R04, R14, R16, R20, C02 | Choose job/thread scope and how ordinary controls/observation remain available. Native AG-UI interrupt reuse is conditional on this decision, not assumed. |
| Capabilities, failure and native projections | Truthful supported behavior, catalog/input modes, typed errors and query/result projection with documented access/order/retention. Unknown and unsupported remain distinct. | Host policy; each Adapter for native contract | R11, R20–R22, R25, C04 | Use real callers to justify optional native features; test each advertised SDK path, including cancel, ListTasks and background output conversion. |

The strongest conclusion is therefore **retain the shared-core direction as a proposal, and deepen its contracts before extraction or adoption**. Neither Adapter must lose required product meaning in principle, but that statement is conditional on filling the gaps above. Both current spikes already lose some original action provenance; neither supplies live Pi progress merely by streaming a completed publication. Using both protocols would not repair either omission in a shared core.
