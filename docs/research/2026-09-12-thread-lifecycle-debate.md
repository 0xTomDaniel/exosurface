## Evidence and limits

The source checks use the previously inspected A2A JS SDK 1.1.0 and AG-UI core/client 0.0.59. Prior executed results remain in the [September 11 recheck](2026-09-11-protocol-recheck.md); the corrected ListTasks probe and binding/version caveats remain in the [September 12 investigation](2026-09-12-protocol-tradeoffs.md). This debate did not rerun those tests.

Relevant primary implementations: [A2A request handler](https://github.com/a2aproject/a2a-js/blob/v1.1.0/src/server/request_handler/default_request_handler.ts), [public event-bus manager](https://github.com/a2aproject/a2a-js/blob/v1.1.0/src/server/events/execution_event_bus_manager.ts), [published AG-UI client](https://unpkg.com/@ag-ui/client@0.0.59/dist/index.mjs), and [published AG-UI core](https://unpkg.com/@ag-ui/core@0.0.59/dist/index.mjs). The [AG-UI interrupt contract](https://docs.ag-ui.com/concepts/interrupts) constrains independent progress when multiple decisions are pending; it does not prohibit multiple interrupts or implement domain approval safety.

Still unvalidated under both candidates: complete Lit/Pi visual and linguistic continuity; browser reconnect during/after work; coherent snapshot-to-live recovery; two-client acceptance and duplicate delivery; cancel/completion races; restart with uncertain writes; slow/stalled observers, client parsing, and retained resource bounds. A2A additionally needs standard-wire cleanup/renewal proof; AG-UI needs complete live/restored association and publication-framing proof. These are essential unknowns, not minor polish.

## Proposed comparison and remaining choice

Use one Exo host, semantic thread store, fixture vault, renderer, and catalog. A2A contributes native multipart communication, task-bound history, and standard work controls; its observer/task/store integration has concrete costs. AG-UI contributes reusable verifier and text/tool/activity/message processing; its supported metadata projection, observation/history conventions, and acknowledged cancellation have concrete costs. Count shared domain and semantic work once.

Run the same complete exchange: create a visual-only agenda; combine an utterance and a selected object; close all clients while work and source edits continue; observe while idle; recover latest state and an original historical referent into Pi; race source updates, acceptance, and cancellation; restart around uncertain effects; test churn, renewal, and slow/stalled consumers. Pin compatible published dependencies and measure actual exceptional paths, resource behavior, and implementation/test burden. The debate recommends this next evidence; it does not authorize deployment or finalize the architecture.

All three protocols together have no demonstrated present consumer or benefit. No dependency patches, forks, copied internal repairs, or replacement SDK are accepted. Full snapshots remain allowed when coherent and reconstructible; durable replay is not automatically required.

## Ratified common statement

The following records the statement accepted on September 12. Its metadata-propagation assertions in clauses 3 and 6 are historical, not current guidance; use the [September 13 correction](2026-09-13-weighted-forecast.md).

1. Independent background execution/lifecycle reliability AND a complete multimodal conversational thread are essential gates. Passing one cannot compensate for failing the other. Neither candidate has passed the complete gates. This debate adds source inspection, not new execution tests, and preserves the exact limits of September 11/12 probes.

2. One Exo host owns admission, independent Pi execution, semantic contributions/authorship, utterances, exact visual/object revisions, causal references, meaningful history, source reconciliation, permissions, acceptance receipts, and model context projection. Both protocols carry projections of that shared model. A turn is not inherently a protocol message/run/task. Neither protocol makes incoming client state authoritative or automatically makes the full visual exchange available to Pi.

3. A2A offers multipart Messages, useful task-bound history, and standard work discovery/cancellation. It does not provide a complete thread archive or observation stream for all contexts/taskless messages. AG-UI offers reusable verification and text/tool/activity/message processing, with supported metadata carriers. Its 0.0.59 live event-to-message metadata propagation needs explicit handling; current activity reduction is not historical preservation. This is a carrier/projection difference, not absence of any association carrier. Semantic meaning and archive responsibility are shared.

4. Proposed comparison mapping: one ordered observer publication path applies current-surface changes under either option; command channels provide admission/status and do not independently apply the same updates. Contributions and publications have enough identity/revision information to suppress duplicates, detect gaps, and reconstruct coherently. History rendering is isolated from current-surface mutation. This is an integration proposal to test, not a ratified implementation architecture. Other mappings must demonstrate equivalent ordering/deduplication.

5. A2A candidate: use supported executor/TaskStore/route seams; tracked work admission is non-streaming with immediate return. Finite renewable observer Tasks are a plausible alternative to forever Tasks. Observer state does not become INPUT_REQUIRED merely because an independent domain proposal is pending. Retire/reconcile stale leases and re-admit publication on restart; a recreated bus alone does not restore its executor/publisher/persistence drain. Early attachment and Task+EOF require an explicit readiness/renewal policy. Use valid task update events, bound task history/artifact content and retired task retention, and measure storage write volume. Artifact replacement limits retained content only if deliberately bounded; it must carry a genuinely reconstructible checkpoint rather than just the last UI delta. Standard-wire client interoperability, renewal consistency, restart, and resource bounds remain untested.

6. AG-UI candidate: use supported run/connect transport and core processing, with separate command and observer client instances in the proposed mapping. Observer publications need valid serialized run framing (including initial snapshots), ordering, and bounded transport/queues. Carry live associations explicitly in supported content/subscriber projection or complete message snapshots; do not assume event metadata automatically appears on accumulated messages. Restore current UI and meaningful history, then project relevant meaning into Pi. Exo defines acknowledged cancellation and archive/discovery semantics. Proposed independent domain proposals use normal validated actions; reserve interrupt/resume for actually blocking interactions. Multiple interrupts can exist, but the all-open-resume/blocked-thread rules constrain independent progress. Client-prepared inputs do not imply client authority. Slow browser/client parsing and server writer behavior remain unproven.

7. Common test sequence: visual-only and combined utterance/selection turns; close every client while scheduled work/source edits continue; observe while idle; restore during and after completed execution; recover the original historical referent into Pi; inject a source edit during recovery/action submission; race two-client acceptance and duplicate delivery; race cancellation/completion; restart at an uncertain write; exercise renewal/churn, slow/stalled consumers, and bounded retained resources. Pin compatible published SDK/A2UI/Lit/catalog versions. Use identical host logic and outputs. Full snapshots are permitted if they restore a coherent view; durable replay is not automatically required.

8. Compare actual candidate-specific responsibilities, exceptional paths, supported SDK processing reused, resource behavior, and implementation/test burden after both gates. Do not count shared semantic/domain work only against one side. A2A's potential advantage is native communication/work contracts; AG-UI's is event-processing reuse and potentially simpler observation integration. Lower total cost remains unmeasured.

9. Current positions after cross-examination: Astra retains a weak conditional A2A preference; Fable retains a very narrow conditional AG-UI preference, effectively even. No shared protocol winner is established. A bounded comparison is the shared next-evidence recommendation, not authorization to silently build/deploy the product. Each can change ranking if the other passes both gates with fewer owned exceptional paths, or their preferred option requires prohibited dependency repairs. If ratification changes either position, revise this clause before publication.

10. No patches, forks, copied SDK-internal repairs, or replacement SDK. Equal latitude for supported Adapters. No present need for all three protocols together; no final protocol/storage/renderer-version choice is made by this debate.
