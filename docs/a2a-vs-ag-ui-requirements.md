# Exosurface requirements: A2UI over A2A versus A2UI over AG-UI

Working comparison, updated September 14, 2026. No protocol or final architecture is selected. This table summarizes the working architecture (kept private); it does not introduce additional requirements. Implementation evidence starts with the [September 11 recheck](research/2026-09-11-protocol-recheck.md), which tested AG-UI client 0.0.59 and A2A JS SDK 1.1.0. The [September 12 investigations](research/2026-09-12-protocol-tradeoffs.md) add pinned binding/skill inspection, a corrected narrow ListTasks probe, and the proposed durable-context model. The [September 13 post-spike debate](research/2026-09-13-spike-debate.md) now audits independent browser/Pi implementations at those SDK versions, records narrower proof claims, and provides a jointly ratified recommendation. These are evidence pins, not a claim about future releases or final dependency adoption.

The problem we are solving is a shared workspace in which Exo helps the user assemble and revise a daily agenda, with an interactive surface that remains useful while the agent works independently, information changes elsewhere, and clients disconnect or switch. A smaller simulated smart-home scenario tests which interaction concepts can also support future devices.

Both candidates retain the same A2UI format, Lit renderer, component catalog, and Exo-owned agent host. The recorded spikes use Pi; harness selection is under review. The alternatives are **A2UI over A2A** and **A2UI over AG-UI**. The AG-UI candidate uses the official SDK through supported Adapters; React and CopilotKit are optional integration choices, not part of its name or a required UI layer. The spikes use independent host implementations against common requirements, not shared executable code. A protocol's ability to represent an interaction is distinct from its SDK implementing reliable persistence, recovery, or cleanup.

**Additional background support is required and now demonstrated in the scoped AG-UI spike.** Supported run/connect/abort overrides retain official verification, state application and subscribers. Exo owns the transport, publication, recovery, renewal and resource handling. The protected default connect throws the not-implemented error; the public connectAgent wrapper catches it and returns an empty result, so successful return alone is not observation. A2A also needs owned observation Tasks, renewal, heartbeat-assisted release and a close-aware route. W1/W3 count this support. Neither result establishes a complete stock-SDK or CopilotKit solution. [Post-spike ownership audit](research/2026-09-13-spike-debate.md#ownership-and-what-the-spike-does-not-establish).

**Core product principle — adopted direction:** Exosurface supports a shared conversational thread whose turns can be expressed through visual interaction, language, or both together. Every meaningful contribution participates in the same evolving context. A surface and an utterance are expressions within that thread; chat is optional. Turn grouping, persistence, and protocol mapping remain open.

**Common UI baseline:** Both candidates carry A2UI surface creation, incremental component/data updates, deletion, and user actions. The same renderer and catalog provide the same intended user experience. Evolving UI, direct manipulation, and an agenda that changes throughout the day are shared requirements, not advantages unique to AG-UI. The [A2UI transport contract](https://a2ui.org/specification/v0.9-a2ui/#transport-decoupling) separates these UI semantics from their delivery.

**Essential under both candidates:** Background execution and lifecycle reliability remain necessary alongside the complete multimodal thread. A stronger communication model does not offset failed recovery, lost work, or unbounded observers. Untested behavior is unknown, not passed.

The [shared-core Interface mapping](shared-core-protocol-mapping.md) traces the original 25 requirements through proposed core representations and each protocol Adapter. It separates actual spike information loss, incomplete core contracts and native capability tradeoffs. Original A2UI provenance is lost at different stages under both spikes; neither demonstrates live Pi progress merely by streaming completed publications. These source findings do not change the scores or pass additional gates.

**September 14 addition — provider portability:** Row 26 records H1, the user's requirement to use and swap model providers without vendor lock-in. It adds the shared, currently unknown gate G7 without changing the historical protocol weights/scores. The precise Interface amendment and harness choice remain open in the provider/harness brief (kept private); the historical 25-row mapping does not claim this new coverage. Pi remains the spike baseline, not a settled harness-selection verdict.

**Comparison method:** Each candidate cell names a **Benefit** and **Cost / limit** in terms of work saved or work Exo must own. A benefit can be shared; it does not imply an advantage over the other option. The last column explicitly states the **Assessment**, **Shared work**, **Evidence**, and **Next** check. “No demonstrated advantage” and “unknown” are valid results. Contract conventions, inspected examples, executed probes, and untested proposals are different evidence levels. Both now have bounded browser/Pi evidence; complete mandatory behavior and lower total integration cost remain unestablished. Reported spike results were audited, not rerun during the debate.

The [weighted comparison](a2a-vs-ag-ui-weighted-comparison.md) groups these requirements into six proposed tradeoff weights, with mandatory requirements assessed separately. It now scores all six criteria with provisional estimates, plausible ranges, confidence and sensitivity. The ratified post-spike assessment narrowly favors A2A, 3.125 versus 3.075, effectively even within judgment uncertainty. The weights are proposals, not accepted requirements. Forecast scores are distinct from the demonstrated behavior assessed in this table. ## The multimodal thread: direction and open design

**Adopted product direction:** A thread is the temporal exchange itself. A2UI presentations and direct user interactions form conversational turns even when there is no chat. Language and visuals can also participate together in one turn: a selected task plus “move this after lunch,” followed by Exo’s visual change and explanation. The surface is an evolving visual expression of that exchange.

**Design still open:** Preserve the meaningful contributions, their referents, and enough historical/current state to continue the conversation. Define turn grouping and how Pi receives the shared interaction context; saved UI alone is insufficient. Both protocol mappings must be evaluated against the same visual-only and combined-modality thread scenarios. This conceptual direction selects neither a wire representation nor a storage schema. - **Protocol contracts:** The [A2A specification](https://a2a-protocol.org/latest/specification/) defines task control and interaction operations. The [A2UI transport section](https://a2ui.org/specification/v0.9-a2ui/#transport-bindings) documents its A2A mapping and identifies AG-UI as an option. These describe available contracts, not a tested Exosurface implementation.
- **AG-UI integration:** The [AbstractAgent documentation](https://docs.ag-ui.com/sdk/js/client/abstract-agent) exposes run/connect extension points. The [published transformer](https://github.com/ag-ui-protocol/ag-ui/blob/release/2026-08-27/sdks/typescript/packages/client/src/transform/http.ts) and our recheck establish the narrower lifecycle concern. [PR 2627](https://github.com/ag-ui-protocol/ag-ui/pull/2627) improved buffers and failure cleanup upstream; those changes were absent from the package tested on September 11 and do not settle all detach paths.
- **A2A integration:** The [released request handler](https://github.com/a2aproject/a2a-js/blob/v1.1.0/src/server/request_handler/default_request_handler.ts) and [Express route](https://github.com/a2aproject/a2a-js/blob/v1.1.0/src/server/express/json_rpc_handler.ts) are the relevant implementations for the persistence and observer-cleanup findings. Candidate remedies were demonstrated in narrow Node tests, not certified for browser use.
- **September 12 follow-up:** The [trade-off investigation](research/2026-09-12-protocol-tradeoffs.md) identifies official A2UI integration guidance and middleware, bounds the sample implementations, and resolves the earlier empty ListTasks result in a narrow corrected probe. It also distinguishes AG-UI pause/resume from active-work cancellation.
- **Multimodal thread follow-up:** The [message/turn mapping investigation](research/2026-09-12-protocol-tradeoffs.md#multimodal-thread-mapping) adds contract/source evidence for native multipart A2A Messages, AG-UI message processing, and the remaining turn/history/model-context responsibilities. It adds no new execution proof.
- **Ratified adversarial review:** The [thread and lifecycle debate](research/2026-09-12-thread-lifecycle-debate.md) records the common statement, concrete observer/metadata corrections, and remaining split. It adds source inspection and proposed mappings, not new execution tests.
- **September 13 completed forecast and correction:** [Two Astra high investigations](research/2026-09-13-weighted-forecast.md) complete the cost forecasts and verify published package source. AG-UI client 0.0.59 does merge metadata on inspected text/activity paths, correcting the earlier blanket claim. A2UI middleware 0.0.10 publication is confirmed. These are source checks and forecasts, not runtime proof.

It corrects the fully chatless AG-UI model claim, weak browser-stall assertion and source-authority gaps. Both reviewers explicitly accepted a narrow A2A recommendation. This audited prior execution; it did not rerun the suites. Complete gates remain unresolved and AG-UI's arbitrary-source-writer case fails.

- **Private work-control follow-up:** The [source/caller audit](research/2026-09-13-private-control-convention.md) distinguishes available A2A contracts from net work removed for Exo clients. It distinguishes a split browser, serial AG-UI-to-A2A bridge and sibling Adapters over one Exo/Pi core. The third avoids serial translation while retaining each protocol's observation obligations. No new score, runtime gate or topology decision is implied.

## What the comparison still needs to answer

The central open question is which leaves less integration work for the same complete conversational exchange: A2A’s native multipart Messages and standard work controls, or AG-UI’s thread/message/event processing. Both need Exo-owned meaning, references, history, and recovery. In the [post-spike adversarial debate](research/2026-09-13-spike-debate.md), both explicitly ratified a narrow A2A recommendation. The ranking has low confidence and does not adopt the architecture or pass every mandatory requirement. The subsequent control-convention audit leaves the value of its deciding W4 advantage under review; there is no new consensus.

The completed packages use independent implementations and the same intended product semantics/renderer. Count shared planning, source, authorization and approval logic once; normalize unequal generation, source-write and fault scenarios. Next verify matched observer faults on the selected implementation and resolve source/capacity safety. A protocol-specific obstacle requiring an A2A SDK repair while AG-UI passes through supported extensions would reverse the recommendation. Findings inform discussion; they do not automatically finalize an architecture.
