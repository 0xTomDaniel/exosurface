Quality gate: one green check per package, debt that only goes down

The Exosurface plugin package has one deterministic check that says whether a change may land. Some gates must be clean; the rest are counts of stricter findings that are recorded and may only go down.

User stories

As a maintainer or an implementing agent, one check in the package tells me whether my change may land, and it says the same on a fresh clone as on my machine.

As the owner, the recorded counts of stricter findings may only go down, so quality debt is paid off over time and never grows back.

Acceptance criteria

Given an implementer, When any change to the package is ready for hand-off, Then the package check is green at the change's head on a fresh clone with dependencies installed from the lockfile; this applies to every feature.

Given an implementer whose change imports a package that is not a listed dependency, When the implementer runs the package check, Then the check fails, naming the dependency gate and the unlisted package, proven by a unit test: no screen shows it.

Given an implementer whose change adds one unused export, When the implementer runs the package check, Then the check fails, naming the unused-exports gate with its count and its baseline, proven by a unit test: no screen shows it.

Given an implementer whose change removes one strictest-type-check error, When the implementer records the baseline, Then the recorded strictest-type-check count is one lower and every other recorded count is unchanged, proven by a unit test: no screen shows it.

Given an implementer whose change adds one lint finding, When the implementer records the baseline, Then recording refuses, naming the lint gate, and the baseline is unchanged, proven by a unit test: no screen shows it.

Modular boundaries

The package check owns every deterministic gate of the package. Caller-facing seam: just check in the package directory, its exit status, and one line per failed gate naming it. Dependency direction: self-contained; it runs only tools pinned in the package's own npm dependencies and calls no network service or model. Observable scope: pass or fail, with each failed gate named and, for a counted gate, its count and baseline.

The ratchet baseline owns the recorded count of every counted gate. Caller-facing seam: a committed file in the package, read by the check and written only by the record step. Dependency direction: self-contained within the package; the check reads it, and the record step writes it from the check's own counts. Observable scope: the counts in the file and in the check's output.

Ratchet

R1 The check compares each counted gate's count with its recorded baseline and fails on any count above it.

R2 A count below its baseline passes, and the check names it as ready to record.

R3 The baseline changes only through the record step, which lowers counts and never raises one.

Running the check

C1 The check runs on a fresh clone after a clean npm install from the package's lockfile; every tool it needs is a pinned development dependency.

C2 The package's agent instructions name the package check as the gate to run before hand-off.
