Pages and activity: one surface, every page its own thread, one shared trunk

The person and Exo work on one surface with one input and no separate chat. Everything is a page made of general blocks, and every page has its own activity: the page shows the work now, the activity shows how it got here. Pages work in parallel, and what each page decides reaches every other page through one shared trunk of commits, so every page feels like the same Exo.

A commit is a one-line record Exo writes to the trunk when a page decides or finishes something, for example "Weekend trip: booked the lake cabin for Friday and Saturday".

Vocabulary follows the glossary: surface, page, stage, version, page edits, press, outline, and the new terms block, Exo block, input, activity, child page, trunk and commit.

User stories

As a person, I work with Exo on one surface with one input that is always there and no chat beside it, so the work we are on is always what I see.

As a person, I read Exo's latest words on the page itself, in one Exo block, so its judgement sits with the work instead of in a transcript.

As a person, I open any page's activity and see how it got here, so the page can stay present tense without losing its past.

As a person, I make a new page with one press, either at the top level or inside the page I am on, so it lands where it belongs instead of in an endless list.

As a person, I work on several pages at once, with Exo working on each, so one topic never waits for another.

As Exo, every turn on every page starts from the same trunk, and a child page's turn also starts from its parent page as it is now, so every page is the same Exo and no page reads another page's half-formed thinking.

As Exo, when a page decides or finishes something, I commit one line to the trunk, linked to where it was said, so every other page knows it at its next turn.

Acceptance criteria

Given a person on a page, When the person types a message in the input and sends it, then waits for Exo to finish its turn, Then the page's Exo block shows Exo's reply, the input is still shown and empty, and the surface shows no chat transcript.

Given a person on a page whose Exo block shows Exo's reply to an earlier message, When the person sends a new message, then waits for Exo to finish its turn, Then the Exo block shows only Exo's reply to the new message.

Given a person on a page Exo has answered once, When the person sends a second message, then waits for Exo to finish its turn, then opens the page's activity, Then the activity lists both of the person's messages and both of Exo's replies, in the order they were said.

Given a person on a page with a button, When the person presses the button, then opens the page's activity, Then the activity lists the press by the button's label, with the values it sent.

Given a person on a page Exo has answered once, When the person types a message in the input without sending it, then opens the page's activity, Then the activity lists the earlier message and Exo's reply, and nothing of the unsent text.

Given a person on a page Exo has changed twice, When the person opens the page's activity, then opens the earlier version from it, Then the page shows as it was at that version, marked as an earlier version.

Given a person on a page where Exo committed a decision, When the person opens the page's activity, Then the activity shows the commit as one line, marked as a commit, next to the Exo turn it came from.

Given a person on the surface, When the person presses the surface's New page button, Then the surface shows a new empty page in view, with the input shown and empty.

Given a person on a page, When the person presses that page's New page button, then goes back to the page they were on, Then that page lists the new page as one of its child pages.

Given a person with two pages, When the person sends a message on one page, then opens the other page before Exo finishes that turn, then waits until Exo finishes its turn on the first page, Then the page the person opened is still the page in view, not pulled back to the first page.

Given a person on a page that lists a child page, When the person opens the child page, then sends a message there, then goes back to the parent page before Exo finishes that turn, Then the parent page lists the child page as active.

Given a person with two pages, When the person sends a message on one page, then opens the other page before Exo finishes that turn, then sends a message there, then goes back to the first page after Exo finishes its turn there, Then the first page's Exo block shows Exo's reply to the first message.

Given Exo on a child page whose parent page has changed since the child's last turn, When the person sends a message on the child page, Then Exo's turn reads the parent page as it is now; no screen shows it.

Given Exo on a page, while another page that is neither its parent nor its child has committed a decision, When the person sends a message on the first page, Then Exo's turn reads that commit line and nothing of the other page's activity; no screen shows it.

Given Exo on a parent page whose child page has committed a decision, When the person sends a message on the parent page, Then Exo's turn reads that commit line, marked as coming from that child page, and nothing of the child's activity; no screen shows it.

Given Exo on a page that decides something in a turn, When the turn ends, Then the trunk holds one new commit line for it, linked to that turn in the page's activity, and nothing else from the turn; no screen shows it.

Modular boundaries

Pages own every page's blocks, its versions, and the tree of parent and child pages. Caller-facing seam: the page tools Exo calls on the page its turn belongs to, and the page the surface renders. Dependency direction: self-contained; activity and the surface depend on pages, and pages depend on neither. Observable scope: what a page shows, its versions, and the child pages it lists.

Activity owns each page's own agent thread: the record of what was sent, pressed, said, versioned and committed on that page. Caller-facing seam: one activity per page, written by the person's sends and presses and by Exo's turns on that page, read by the activity view and by Exo's turns on that page only. Dependency direction: external provider OptChat, as each page's own conversation; an activity points at page versions and writes commits to the trunk, and no activity reads another. Observable scope: the activity view of a page, and the Exo block, which shows the latest Exo turn.

The trunk owns the shared record of commits for all of the person's pages. Caller-facing seam: a commit appends one line linked to its activity entry; every Exo turn reads the trunk. Dependency direction: external provider OptChat, as one conversation that holds only commits, so it stays readable as it grows; activities depend on the trunk, and it depends on no page. Observable scope: the commit lines Exo reads each turn, and commits shown in a page's activity.

The surface owns what the person sees and does: the page in view, the input, the New page buttons and the activity view. Caller-facing seam: a send or press goes to the activity of the page it was made on. Dependency direction: self-contained within the package; it depends on pages and activity, and nothing depends on the surface. Observable scope: everything on screen.

The surface

S1 The surface shows the page in view and one input; it has no chat column and no transcript.

S2 The input is always shown, and what the person sends from it is a turn in the activity of the page in view.

S3 A press of a button on a page is a turn in that page's activity.

S4 Waiting on a brainstorm with Exo: when Exo's turn on the page in view may make a new page or change which page is in view, for example when the topic changes. Tom: "Quite often Exo rightfully creates a new page because the topic has changed", he will often want one general-purpose Exo home where the topic changes, sometimes a topic change should become a durable separate thread and sometimes not, and sometimes he wants a dedicated page and thread that is always available.

S5 A turn on a page that is not in view never changes which page is in view.

S6 The surface's New page button makes an empty top-level page, which starts from the trunk alone; a page's own New page button makes an empty child of that page. Either puts the new page in view.

How does the person reach a page that is not in view? This depends on the S4 brainstorm. With top-level pages and child pages, the pages form a tree, which a sidebar shows whole.

Pages

P1 A page is made of general blocks from the visual catalog; no page or block is specific to plans, weeks or any other domain.

P2 Every page has exactly one activity and may have child pages; a child page has exactly one parent, and a top-level page has none.

P3 A parent page lists its child pages by title, and opening one puts it in view.

P4 Exo works on several pages at the same time; a turn on one page never waits for a turn on another.

P5 Wherever a page is listed, it shows as active while Exo works on it.

P6 Every page is worked on by the same Exo, with the same identity, vault and trunk.

P7 A page and its activity are one record with two views: the page shows it now, and the activity shows how it got here.

Exo opening a child page on its own to work on something in parallel, and pinning pages.

The Exo block

E1 Every page has one Exo block, which shows Exo's words from its latest turn on that page.

E2 Each Exo turn replaces the block's words; earlier words stay in the page's activity as the turns they belong to.

E3 A turn that only changes the page leaves the Exo block empty, so no earlier words sit beside a changed page.

E4 While Exo works on the page, the Exo block says so.

E5 The Exo block carries what the page cannot, such as judgement or a caveat, and never repeats what the page shows.

E6 When Exo needs something from the person, the page's own inputs ask for it, and the Exo block only points to them.

E7 Only Exo writes the Exo block; the person answers through the input.

The trunk and what each turn reads

K1 The trunk is one shared record of commits for all of the person's pages; each page's activity is a branch off it.

K2 Every commit links to the activity entry it came from.

K3 The trunk holds only commits; no message, draft or reasoning from any page enters it.

K4 No turn reads another page's activity, except the one entry Exo opens by following a commit's link.
