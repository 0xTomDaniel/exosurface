Page bounds: defined once, told to Exo, named on rejection

Exo draws and edits pages with update_exosurface, written in the snapshot format. Every bound the page tool enforces is declared once, and both the tool contract Exo reads and the rejection Exo receives are made from that one declaration, so a page drawn within the contract is never rejected for a bound Exo could not know.

Vocabulary follows the glossary: page, ref, snapshot format, page history.

User stories

As Exo, the page tool's contract tells me every bound a page must stay within, with its value, so a page I draw within the contract is accepted.

As Exo, a rejected call tells me which bound it broke, where on the page, and the bound's value, so I fix that element and send again instead of cutting content.

As a maintainer, I change a bound in one place and the validator, the tool contract and the rejection all follow, so they cannot drift apart.

Acceptance criteria

Given Exo with the page tools, When Exo starts a request, Then the page tool's contract states every page bound the validator enforces, each with its value and the role, attribute, page or call it applies to, in the snapshot format's words, proven by a unit test: no screen shows it.

Given a maintainer whose change makes the validator enforce a page bound the tool contract does not state, When the maintainer runs the package check, Then the check fails, naming that bound, proven by a unit test: no screen shows it.

Given Exo drawing a page in which one element's text is longer than its bound, When Exo sends the page, Then the rejection names the page, that element's ref, the attribute and the bound's value, in the words the tool contract uses, proven by a unit test: no screen shows it.

Given Exo drawing a note with a tone that only other elements accept, When Exo sends the page, Then the rejection names the note's ref and lists the tones a note accepts, proven by a unit test: no screen shows it.

Given Exo drawing a page with more components than a page may hold, When Exo sends the page, Then the rejection names the page, the bound and its value, and the page's count, proven by a unit test: no screen shows it.

Modular boundaries

The bounds definition owns every page bound and its value. Caller-facing seam: one declaration inside the package, read by the validator, the tool contract and the rejection text. Dependency direction: self-contained; it depends on nothing else in the package, and the three readers depend on it. Observable scope: the values Exo sees in the tool contract and in rejections.

The page validator owns accepting or rejecting a call. Caller-facing seam: the update_exosurface result, either the new revision or one rejection message. Dependency direction: self-contained within the package; it reads the bounds definition and never holds a bound value of its own. Observable scope: the rejection text Exo receives.

The tool contract owns what Exo is told about valid pages. Caller-facing seam: the update_exosurface description Exo receives with every request. Dependency direction: self-contained within the package; generated from the bounds definition. Observable scope: the description text.

What counts as a page bound

B1 A page bound is any check the page tool applies that a call written in the snapshot format can break.

B2 A check the snapshot translation always satisfies, such as data nesting or binding paths, is not a page bound.

B3 The pages on the surface and the surface's total size are kept by the system, which moves older pages into page history; they are page bounds only where one call alone breaks them.

B4 Every page bound and its value are declared once, in the bounds definition; no other code or text holds a bound's value.

Families of page bounds; the bounds definition holds each bound and its value

Text lengthEvery text attribute: titles, labels, values, details, notes, cells, captions, units, summaries

How Exo is told

T1 The update_exosurface contract states each bound beside the role or attribute it applies to, in the snapshot format's words, never the renderer's component names.

T2 No other agent-facing text, such as the presentation guide or the optional reference skill, states a bound's value; where it needs one, it points to the tool contract.

T3 A rejection names the page, the element by its ref, the attribute, the bound and its value, in the tool contract's words; a bound on the whole page or call names the page or call instead of an element.

T4 A rejection is plain words, never raw schema output.

Non-goals

Choosing bound values: the bounds definition holds them, and this spec sets none.

The legacy A2UI page tools, which stay registered only to read old history and are never offered to Exo.
