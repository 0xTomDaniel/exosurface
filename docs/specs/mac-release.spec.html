Mac release: install, first run, update and removal of Exo in BB

A new owner installs Exo on their own Mac, inside an unmodified BB, from one versioned release. The release carries Exosurface and the owner service, and a separate generic starter gives the owner a vault of their own. The owner signs Exo in with their own model provider account, starts Exo from BB without a terminal, and keeps their vault and Exo's history through restarts, updates, rollbacks and removal. The Exo the owner uses always runs a fixed release, never a development checkout.

Vocabulary follows the glossary: Exo, surface, Home, page and activity. An owner is the one person an install belongs to. A release is one immutable, versioned build. The owner service is the background process that keeps Exo's conversation running while BB is closed. The starter is the generic vault and skill set a new owner begins with.

User stories

As a new owner with BB on my Mac, I install Exo with one documented command that checks what my Mac is missing before it changes anything, so I never assemble Exo by hand.

As a new owner, I am told plainly, before anything is installed, that Exo acts with my account's full access, so I consent knowing what it can do.

As a new owner, I sign Exo in to a model provider with my own account, so nothing of anyone else's accounts, keys or proxies comes with Exo.

As a new owner, the first time I open BB after installing, I start Exo from one place and it answers me, with no terminal and no earlier history, so my first minute is a working Exo.

As an owner, BB shows me one Exo entry and offers no test, fixture or clone Exo anywhere, so I can never pick a broken Exo.

As an owner, quitting BB, restarting my Mac and signing back in keep Exo running with its history and my vault unchanged, so Exo is always where I left it.

As an owner, I update to a newer release and roll back to the release before it without losing history, and a rollback my data cannot safely go back to is refused with the reason, so updating is never a gamble.

As an owner, I remove Exo and my vault and Exo's history stay unless I ask for them to be deleted too, so trying Exo costs me nothing.

As an owner, when Exo does not answer, I run one check that names what is wrong and where Exo's logs are, so I can fix it or report it.

As a new owner without a vault, I begin with a generic starter vault that holds no one else's notes, habits, people or accounts, so Exo starts as mine.

As the author, a release holds only the files its allowlist names and never a conversation history, review evidence, credential, personal path or name, so sharing a release shares nothing private.

As the author, the Exo I use day to day runs an installed release, and my development and staging checkouts never change it until I install a release on purpose, so switching a branch never changes the Exo I rely on.

Acceptance criteria

Given a new owner on a Mac with BB and without one tool the install needs (a fixture must be added to provide it), When the owner runs the documented install command, Then the install stops before changing anything and names the missing tool and how to get it.

Given a new owner on a Mac with BB and every tool the install needs (a fixture must be added to provide it), When the owner runs the documented install command, Then before anything is installed the owner reads that Exo and its BB plugin run with the owner's full account access, can read and change any file the account can, run commands and use the network, and act in every account the owner signs Exo in to, and the install waits for the owner to agree.

Given a new owner reading the full-access statement during install (a fixture must be added to provide it), When the owner declines, Then the install ends saying nothing was installed.

Given a new owner reading the full-access statement during install (a fixture must be added to provide it), When the owner declines, Then the Mac holds no Exo release files, owner service or BB plugin; no screen shows it.

Given a new owner on a Mac with BB, every tool the install needs and no vault (a fixture must be added to provide it), When the owner runs the documented install command, then agrees to the full-access statement, then waits for it to finish, Then the install reports the installed release's version, where the owner's new starter vault is, and that the next step is opening BB.

Given a new owner whose Mac already holds a vault with notes in it (a fixture must be added to provide it), When the owner runs the documented install command naming that vault, then agrees to the full-access statement, then waits for it to finish, Then every note that was in the vault is unchanged, and the install reports which starter files it added beside them.

Given a new owner whose vault already holds a file with the same name as a starter file (a fixture must be added to provide it), When the owner runs the documented install command naming that vault, then agrees to the full-access statement, Then the install stops before changing anything, names each file that is in the way, and the vault is unchanged.

Given a new owner who has just installed Exo (a fixture must be added to provide it), When the owner opens BB, Then BB's sidebar shows one Exo entry and no other Exo thread.

Given a new owner who has just installed Exo (a fixture must be added to provide it), When the owner opens BB, then starts a new BB thread, then opens its model picker, Then the model picker offers no offline, fixture, live trial or clone Exo.

Given a new owner who has just installed Exo and has not signed in to a model provider (a fixture must be added to provide it), When the owner opens BB, then opens the Exo entry, Then the Exo entry asks the owner to sign in with their own model provider account and shows no reply from Exo yet.

Given a new owner who has just installed Exo and signed in to a model provider (a fixture must be added to provide it), When the owner opens the Exo entry, then starts Exo, then sends "hello", then waits for Exo to finish its turn, Then Home shows Exo's reply on a page Exo drew, and Home shows no earlier conversation.

Given a new owner on Home after Exo's first reply, on a page with a button (a fixture must be added to provide it), When the owner presses the button, then waits for Exo to finish its turn, Then Home shows Exo's reply to that press.

Given a new owner whose first start of Exo stopped partway (needs an induced failure: the owner service exits during first start), When the owner opens the Exo entry, then starts Exo again, then sends a message, then waits for Exo to finish its turn, Then Home shows Exo's reply, and BB's sidebar still shows one Exo entry.

Given a new owner who has just installed Exo and signed in to a model provider (a fixture must be added to provide it), When Exo answers the owner's first message, Then Exo's request went to the provider the owner signed in to, with the owner's own sign-in, and through no proxy the owner did not set up; no screen shows it.

Given an owner on Home with a conversation with Exo (a fixture must be added to provide it), When the owner quits BB, then opens BB again, then opens the Exo entry, Then Home shows the same conversation and pages as before BB quit.

Given an owner on Home with a conversation with Exo (a fixture must be added to provide it), When the owner restarts the Mac, then signs back in, then opens BB, then opens the Exo entry, then sends a message, then waits for Exo to finish its turn, Then Home shows Exo's reply after the same conversation as before the restart.

Given an owner on Home with a conversation with Exo whose owner service has just exited (needs an induced failure: the owner service process ends), When the owner sends a message, then waits for Exo to finish its turn, Then Home shows Exo's reply after the same conversation as before the service exited.

Given an owner with a conversation with Exo on one release and a newer release available (a fixture must be added to provide it), When the owner runs the documented update command, then opens BB, then opens the Exo entry, then asks Exo which release it runs, then waits for Exo to finish its turn, Then Home shows the earlier conversation followed by Exo's reply naming the newer release's version.

Given an owner who updated to a newer release that kept Exo's data readable by the release before it (a fixture must be added to provide it), When the owner runs the documented rollback command, then opens BB, then opens the Exo entry, then asks Exo which release it runs, then waits for Exo to finish its turn, Then Home shows the earlier conversation followed by Exo's reply naming the earlier release's version.

Given an owner who updated to a newer release that changed Exo's data in a way the release before it cannot read (a fixture must be added to provide it), When the owner runs the documented rollback command, Then the rollback stops before changing anything and says the earlier release cannot read Exo's current data, and the newer release keeps running.

Given an owner with Exo installed, a vault and a conversation with Exo (a fixture must be added to provide it), When the owner runs the documented removal command without asking to delete data, Then the removal reports that Exo's plugin, service and release files are gone and names where the kept vault and Exo's kept history are.

Given an owner who has just removed Exo without asking to delete data (a fixture must be added to provide it), When the owner opens BB, Then BB's sidebar shows no Exo entry.

Given an owner who removed Exo without asking to delete data (a fixture must be added to provide it), When the owner runs the documented install command again, then agrees to the full-access statement, then opens BB, then opens the Exo entry, Then Home shows the conversation from before the removal.

Given an owner whose Exo does not answer because its owner service is not running (needs an induced failure: the owner service is stopped and kept from starting), When the owner runs the documented check command, Then the check names the owner service as not running, says how to start it, and names the folder that holds Exo's logs.

Given the author with a built release (a fixture must be added to provide it), When the author runs the release's privacy check, Then the check passes only when every file in the release is on the release's allowlist and none holds a conversation history, review evidence, credential, the author's paths or names, or a proxy address.

Given a new owner who has just installed Exo with no earlier vault (a fixture must be added to provide it), When the owner searches the starter vault for the author's name, company, colleagues, accounts or home folder, Then the search finds nothing.

Given the author with Exo running from an installed release and a development checkout of Exosurface (a fixture must be added to provide it), When the author switches the checkout to another branch, then restarts the owner service, then asks Exo which release it runs, then waits for Exo to finish its turn, Then Exo's reply names the installed release's version.

Modular boundaries

The release owns one versioned, immutable build: the production plugin with its prebuilt files, the owner service's source, the exact versions of Pi, OptChat, Node and BB it was built against, the data format version it writes and the ones it reads, and its allowlist. Caller-facing seam: one release manifest beside the production plugin, which the installer and the privacy check read. Dependency direction: self-contained; the installer and the privacy check depend on the release, and the release depends on no installed Mac. Observable scope: the version Exo reports and what the privacy check finds.

The installer owns the check before install, the full-access statement, install, update, rollback, removal and the check command, including the background service definition and its logs. Caller-facing seam: the documented install, update, rollback, removal and check commands. Dependency direction: external providers macOS launchd and BB's plugin commands; the installer depends on the release and on a rendered starter, and nothing in a release depends on the installer. Observable scope: what each command reports, the one Exo entry in BB, and whether the owner service runs.

The production plugin owns Exo's one entry in BB, the Exo models BB offers, first start, and the surface the owner sees. Caller-facing seam: the Exo entry and its start control in BB; the owner service it talks to. Dependency direction: external provider BB through its plugin SDK; depends on the owner service; the surface behaves as pages and activity states. Observable scope: BB's sidebar, BB's model picker, and everything inside the Exo entry.

The owner service owns Exo's running conversation, the new owner's own Pi sign-in and settings, the data format marker, and keeping the conversation through quits and restarts. Caller-facing seam: the plugin's requests for turns and presses, and the data format version the installer reads before an update or rollback. Dependency direction: external providers Pi, OptChat and the owner's model provider; reads the owner's vault; depends on nothing in BB. Observable scope: Exo's replies, its history after restarts, and the version it reports.

The starter owns the generic vault, agent instructions and approved general skills a new owner begins with, and the owner's time zone and name settings in it. Caller-facing seam: a render command that writes the starter into a named vault folder, adding files only and changing nothing when any file is in the way, and a verify command that checks a rendered vault. Dependency direction: external, kept in the Exocortex instance repository; the installer calls its render, and the starter depends on no release. Observable scope: the starter vault's files and the skills Exo can use on a new install.

Lifecycle

  1. Check: report what is missing, change nothing
  2. Full-access statement: the owner agrees or nothing is installed
  3. Install: release, starter render, service, plugin
  4. Sign in: the owner's own provider account
  5. First start: Home, once
  6. Use: survives quit, service exit, restart
  7. Update or rollback: data format checked first
  8. Remove: vault and history kept unless asked

I1 One documented command installs a release, and it changes nothing until its check passes and the owner agrees to the full-access statement.

I2 The check names every missing tool, each with how to get it; it never installs a tool on its own.

I3 Everything the running Exo loads, the plugin BB loads and the code the owner service runs alike, comes from one installed release, never from a source checkout.

I4 The owner service starts when the owner signs in to the Mac, starts again when it exits, finds every program it runs by an absolute path the install recorded, and writes its logs to one named folder.

I5 Install, update and rollback never change or delete a note in the owner's vault; the starter render only adds files, and when any starter file would land on an existing file it adds none and names every such file.

I6 Running install again for the same release changes nothing that is already right and repairs what is missing.

Full access and accounts

T1 Exo is not sandboxed: the owner service and the BB plugin run as the owner, with the owner's full access to files, commands, network, and every account the owner signs Exo in to; Exo's instructions ask before risky actions, but nothing technical stops it, and the full-access statement says so in those terms.

T2 A new install keeps its own Pi settings and sign-ins, separate from any Pi setup the owner already has; it never copies, links or reads another Pi home, sign-in, key, MCP configuration or proxy setting.

T3 A new install sends model requests straight to the provider the owner signs in to; a proxy is used only when the owner sets one up.

T4 A new install connects no paid integration and no third-party account until the owner adds it.

First start and the one entry

R1 BB shows one Exo entry, which opens Home; Exo's backing threads, helpers and earlier test threads never show as other Exo entries.

R2 The Exo models BB offers are only the production ones; offline, fixture, live trial and clone modes are not in a release.

R3 First start makes Exo's new, empty conversation and its backing BB thread once, before the owner service serves it; starting again after a partial first start finishes it without making a second conversation or entry, and never replaces an existing conversation.

R4 First start needs no earlier conversation, thread, profile or memory, and creates no memory content Exo did not write itself.

How the Exo entry shows Home in BB: as an Exosurface page with Exo's chat beside it (page first), or as BB's own thread view with Home's pages in its side panel (chat first). The first-start screen's mockups wait on this answer.

Releases, update and rollback

L1 A release never changes once built; a fix is a new release with a new version.

L2 An install keeps the releases it has installed side by side, and exactly one of them is current; update and rollback only change which one is current.

L3 Exo's data carries the version of its format; every release states the format it writes and the formats it reads, and update or rollback to a release that cannot read the current format is refused before anything changes.

L4 A release states the exact Pi and OptChat versions and the lowest Node and BB versions it was built against, and the install check refuses a Mac that cannot meet them.

L5 Exo can tell the owner which release it runs.

How a new owner receives a release: as a built, versioned archive the author hands over, or by installing from a version tag of the private repository, which needs the owner to have repository access.

D2 The check command changes nothing.

The author's own Exo and staging

G1 The author's own Exo is an install like any owner's: it runs a release and keeps its existing history and vault, which its configuration names.

G2 Staging runs a release too, with its own data, and never shares a conversation, sign-in or service with the author's own Exo.

Whether staging can run in a BB kept apart from the author's own BB on the same Mac account.

Non-goals

What happens on Home and on other surfaces once Exo is running, which pages and activity owns; several surfaces at once need several conversations under one Exo, and this spec does not decide how the owner service runs them.

Public distribution, an App Store or notarized app, automatic updates, Windows or Linux, and more than one owner per Mac account.

Moving the author's existing Exo onto a release, which is a one-time task, not product behavior.
